# Start Here

This project is governed by the `/docs` App Spine. Product direction, implementation sequencing, unresolved decisions, and current build status must be read from the docs before work begins.

## Operating Model

- Read `AGENTS.md` first.
- Read all numbered docs in `/docs`.
- Use `/docs/09-build-status.md` to understand the current phase and last completed task.
- Use `/docs/07-roadmap.md` to identify the next sequenced task.
- Use `/docs/08-decisions-log.md` and `/docs/10-decision-gates.md` before changing direction.
- Use `/progress/index.html` only as a stakeholder visualization layer, not as source of truth.

## Strategic Evolution

Strategic conversations may require App Spine updates before implementation. A new product idea can change onboarding philosophy, UX assumptions, data boundaries, AI behavior, compliance posture, or architecture.

Not every conversation should trigger product feature code. When a conversation introduces a major idea, the correct first step is impact analysis, documentation synchronization, Decision Gate review, and roadmap sequencing.

Architecture evolution may happen before coding. If the existing guided intake model is affected by conversational onboarding, AI-guided onboarding, progressive onboarding, state-based onboarding, or onboarding orchestration, the App Spine must be updated first.

## Onboarding Evolution

The current product includes a guided 13-step intake for Complete Package and Florida LLC paths. Future onboarding evolution may add or change:

- Conversational onboarding systems.
- AI-guided onboarding assistance.
- Progressive onboarding UX.
- State-based onboarding flows.
- Onboarding orchestration concepts.

These concepts must be treated as strategic architecture changes until Decision Gates are reviewed and sequencing is confirmed.

## Before Coding

If the request is strategic, do not code first. Summarize the impact, identify App Spine updates, create or update Decision Gates, recommend the next non-code step, and wait for confirmation.
